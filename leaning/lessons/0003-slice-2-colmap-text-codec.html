Lesson 3 · about 25 minutes

Build the COLMAP text reader from blocks

Learn the TypeScript ideas behind Slice 2: strict byte decoding, exact token grammar, two-line image records, typed construction, contextual failures, and validated model assembly. You connect the blocks; this lesson does not provide the finished reader.

Your tangible win: sketch the complete reader and explain exactly where malformed text, unsupported recorder data, invalid models, and pose-mapping mistakes are caught.

1. The reader is one trust pipeline

text bytes→ candidate records→ validated model

The reader proves that bytes obey the supported recorder text grammar, constructs all candidate records, then asks the Slice 1 validator to prove model-level meaning. Canonical writing begins in Slice 3.

Parser owns

UTF-8, physical lines, comments, token counts, numeric lexemes, file/line/field context, and construction of candidate records.

Validator owns

Positive safe IDs, finite values, uniqueness, references, PINHOLE support, quaternion norm, and empty public observations/tracks.

Do not let the codec learn ZIP paths or image bytes. It receives three named Uint8Array payloads and returns one validated model. The later adapter owns the archive.

2. Block A — strict bytes to trustworthy text

A normal decoder may replace malformed byte sequences with �. That would repair corrupt input silently. Fatal mode makes malformed UTF-8 observable as an error. 

new TextDecoder("utf-8", { fatal: true });

// Before decoding, recognize and reject the three UTF-8 BOM bytes:
// EF BB BF

Check the BOM in the original bytes. This is clearer than relying on the decoder's easy-to-misread ignoreBOM option. After decoding, reject NUL and normalize only accepted line endings:

  1. Convert CRLF pairs to LF.
  2. If any carriage return remains, it was bare and must fail.
  3. Split on LF while retaining physical line positions.
  4. Allow the final empty array item caused by an optional final LF.

Wrap a decoder TypeError in ColmapError with kind: "syntax", the logical file path, and the original error as its cause. Never return text collected before the failure.

3. Block B — preserve physical lines

Before the first data record, blank lines and comment lines may be ignored. Once data begins, comments are invalid. The important trap is images.txt: each image owns a second physical line, and that line must be empty for the supported recorder profile. 

pose line
empty observation line
pose line
empty observation line

Therefore, do not start with lines.filter(line => line.trim() !== ""). It deletes evidence that each image record has its required second line. Instead, skip preamble lines only until the first data line, then let each file parser consume its own physical structure.

4. Block C — validate lexemes before converting numbers

JavaScript's converters accept more syntax than this recorder profile. For example, Number("") is zero, Number("0x11") is seventeen, and parseInt("12oops") is twelve. Conversion alone is not grammar validation. 

const unsignedIntegerToken = /^(?:0|[1-9][0-9]*)$/;
const floatToken =
  /^-?(?:0|[1-9][0-9]*)(?:\.[0-9]+)?(?:[eE][+-]?[0-9]+)?$/;

Each small numeric reader has two stages:

  1. Match the complete token against its accepted lexical grammar.
  2. Convert with Number and attach field/line context.

The Slice 1 validator still checks semantic rules such as safe integer, positivity, finiteness, and RGB range. This is deliberate overlap at two different levels: the codec proves spelling; the validator proves meaning.

Predict before running

Sort these into accepted unsigned integer, accepted float only, or rejected: 0, -0, 01, 1., 1e-3, +1, .5. Then check against the two expressions.

5. Block D — exact arity before typed construction

Check token count before reading indexes. This turns a vague undefined conversion into one clear syntax error.

Record Exact tokens Meaning
Camera 8 ID, model, dimensions, four PINHOLE intrinsics
Image pose 10 ID, WXYZ quaternion, translation, camera ID, name
Point3D 8 ID, XYZ, RGB, error

With noUncheckedIndexedAccess, an indexed token is typed as possibly undefined. A non-null assertion is reasonable only immediately after your exact arity check establishes that the slot exists. It is not a replacement for checking untrusted input. 

if (tokens.length !== expectedCount) {
  // throw contextual syntax failure
}

// Only after that check:
const firstToken = tokens[0]!;

6. Block E — one narrow parser per file

cameras.txt

Read one data line, require eight tokens, retain the model token long enough to distinguish unsupported OPENCV from malformed syntax, then construct the camera candidate. The validator owns the final “exactly one PINHOLE camera” rule.

images.txt

Use a cursor over physical lines. Read a ten-token pose line, then advance exactly once and require an empty or ASCII-whitespace observation line. A non-empty observation line is unsupported-profile, because general COLMAP supports observations but recorder profile 1A does not.

points3D.txt

Require eight base tokens. Extra valid-looking track tokens are unsupported-profile; malformed base fields are syntax. Construct track: [] only after the text proves that no track data was supplied.

Private candidate shapes may be slightly wider than the public model, such as holding a camera model token as string. That lets runtime validation reject untrusted values honestly instead of lying to TypeScript with an early assertion to "PINHOLE".

7. Block F — assemble once, validate once

The public parse facade coordinates the three independent file parsers, assembles one candidate model, calls the existing Slice 1 validator, and returns only after the complete model passes. 

decode each payload
→ parse cameras, images, points
→ assemble one candidate model
→ validate the whole model
→ return the complete model

This ordering is why a valid-looking image can still fail with kind: "reference": only the complete model knows whether its camera ID exists. Do not return partial arrays if a later file fails.

8. Block G — protect pose meaning with a non-identity fixture

Identity rotation [1, 0, 0, 0] is too symmetrical. A parser could reorder several zero components and the test would still pass. Use a normalized non-identity WXYZ quaternion and a translation whose components are all different. 

qvec: [0.7071067811865476, 0, 0.7071067811865476, 0]
tvec: [1, -2, 3]

Assert that parsing assigns QW, QX, QY, QZ, TX, TY, and TZ to those exact model slots. Slice 2 does not invert poses, compute camera centers, apply WebXR/COLMAP basis conversion, or write the model back to text.

Explain the failure this catches

Why would [1, 0, 0, 0] fail to reveal an accidental WXYZ/XYZW reorder? Say your answer aloud before continuing.

9. Test the seams, not private helper choreography

Test group Main evidence
Strict decode Invalid UTF-8, BOM, NUL, bare CR; LF/CRLF accepted
Lexical grammar Accepted decimals/exponents and rejected broad JS forms
Camera records Exact arity, PINHOLE layout, contextual failures
Image records Two physical lines, empty observations, non-identity pose
Point records Zero/many points, exact base fields, tracks unsupported

Use it.each for token spelling cases; keep one readable end-to-end fixture for each file grammar. Assert structured kind, path, line, and field where applicable, not the full prose message.

10. A safe assembly order for your session

  1. Write one strict-decode test and the smallest decoder block.
  2. Write table-driven integer and float token tests.
  3. Parse one valid camera row, then its malformed cases.
  4. Parse one valid point row and prove extra tracks are unsupported.
  5. Parse one two-line image record with a non-identity pose.
  6. Assemble all three parsers and call the Slice 1 validator.
  7. Run formatting, lint, both typechecks, build, and unit tests.
Explain it to Mingna in one sentence: “The reader proves the spelling and structure of three text payloads, then the existing validator proves the assembled model's meaning before it is returned.”
