Lesson 2 · about 20 minutes

Connect Slice 1's TypeScript blocks

Learn what each file and helper is responsible for, why the pieces stay separate, and how to assemble them test-first without receiving a finished validator.

Your tangible win: sketch the validation pipeline and explain which guarantees come from TypeScript, which require runtime checks, and which belong at the package boundary.

1. Start with the central distinction

Compile-time shape

model.ts helps the compiler and your editor. Its declarations describe intended data, but they disappear from the emitted JavaScript.

Runtime evidence

validate.ts examines actual numbers, names, IDs, and relationships. This is what protects later code from parsed or externally supplied values.

A value can be typed as CameraId and still be -4, because the alias is another name for number. Likewise, a tuple guarantees four slots to checked TypeScript callers, but runtime data can still contain NaN or a bad quaternion norm. Slice 1 needs both layers.

2. Understand the blocks in model.ts

Semantic aliases

CameraId, ImageId, and Point3DId tell a human what a number means. They improve signatures and reviews, but they are not branded types: TypeScript can still allow one numeric alias where another number is expected.

Readonly tuples

A tuple such as readonly [number, number, number] fixes the number and position of components. This is ideal for XYZ and RGB. The quaternion name adds the missing semantic promise: Wxyz tells you the order is [qw, qx, qy, qz].

readonly is compile-time protection, not deep runtime freezing. That is why a no-mutation test still matters.

Interfaces and the literal camera model

Interfaces group named fields. The literal type "PINHOLE" is stronger than string: it states the only accepted variant today. The ColmapCamera alias is a future union seam, so a later reviewed camera type can be added deliberately instead of weakening today's contract.

Pose meaning is part of the type name

WorldToCameraPose prevents a dangerous conceptual shortcut. COLMAP's tvec is translation in the world-to-camera transform; it is not the camera's world position. The validator checks values only. It must not invert, reorder, normalize, flip, or recenter the pose.

Arrays preserve order; IDs express relationships

The arrays retain source record order, while IDs may be sparse and out of order. Therefore, an image's cameraId is resolved by membership in a camera-ID set—not by using the ID as an array index.

3. Treat validate.ts as a sequence of gates

A validator is easier to reason about when it has a visible order. Each gate either throws one contextual ColmapError or allows the unchanged model to continue.

  1. Check that there is exactly one camera.
  2. Validate that camera and record its ID in a local set.
  3. Check that at least one image exists.
  4. Validate image values, uniqueness, names, poses, and references.
  5. Validate point values and point-ID uniqueness.
  6. Reject populated observations or tracks as unsupported profile.
  7. Return or confirm the original complete model unchanged.

Small predicate helpers reduce repetition, but each should express one rule: positive safe integer, finite number, safe filename, RGB channel, or unit quaternion. Keep error creation near enough to the field being checked that kind and field stay accurate.

Why Number.isSafeInteger?

JavaScript numbers cannot represent every large integer exactly. Integer-like IDs and dimensions need positivity plus safe-integer status. A check for “no decimal point” alone would miss unsafe values.

Why Number.isFinite?

Arithmetic comparisons do not reliably communicate the whole rule. Intrinsics, translation, XYZ, and error must reject NaN and both infinities. The non-coercing static method also avoids accepting numeric strings.

Quaternion tolerance

Compute the norm from all four components and compare its distance from 1 with the accepted tolerance, 1e-6. This is a validation check, not an invitation to normalize. Rejecting exposes bad input; repairing would hide it.

4. Use one error class as structured data

ColmapError is a stable envelope. Its kind answers what category failed; optional path, line, and field locate it; optional cause preserves an underlying failure. Slice 1 primarily exercises validation, reference, and unsupported-profile.

Tests should assert the class and structured properties. Exact full messages are deliberately not the contract, so wording can improve without breaking every test.

5. Build the tests as a ladder

Begin with one factory that returns a minimal valid model. Each test changes one fact and names one expected outcome. This gives failures a single cause and keeps the validator's growth visible.

Happy path

Accept the model and prove it is returned unchanged. Add sparse IDs, non-numeric source order, non-identity pose, zero points, and multiple points as separate valid cases.

Focused failures

One test per rule family: IDs, camera, image/name/reference, pose, point/RGB/error, and unsupported profile.

Mutation evidence

Keep a before value and verify validation neither changes content nor replaces the successful model unexpectedly.

Shallow-copy trap: changing a nested field through a shared object can accidentally mutate the base fixture. When overriding a nested camera, pose, or intrinsics field, create new objects along that path.

For thrown errors, capture the error once and inspect instanceof, kind, and field. Avoid calling the validator repeatedly in separate assertions, because each assertion should describe the same failure.

Test-design drill

Write only three test names before implementation: one valid sparse-ID case, one missing-camera reference, and one populated-track case. Under each name, write the expected error kind. Do not write the validator yet.

6. Protect index.ts as a product boundary

A declaration being exported from its own file does not automatically make it part of the package's supported subpath. The barrel file chooses the public contract. Type-only exports disappear from JavaScript; ColmapError remains because consumers need the runtime class for instanceof.

The supplied Slice 1 brief says the low-level validator stays internal and unfinished operations should not be exported. A public API test should prove that the built ./colmap subpath loads and has only intentionally supported runtime values.

Repository review point: the current index.ts also exports later-slice contract types such as comparison and round-trip types. Do not remove them blindly. Compare the Slice 1 brief with accepted team decisions and record the resolution because those sources currently pull in different directions.

Browser compatibility is about the production graph

Build configuration may use node:path; it runs as tooling. The browser-compatible promise concerns production modules reachable from src/colmap/index.ts. Keep Node globals and filesystem APIs out of that graph: no node:fs, Buffer, process, AppFramework, or RecorderApp.

7. Your assembly order

  1. Read the existing model and error declarations; do not duplicate them.
  2. Choose and name the validator boundary according to the accepted contract.
  3. Make one valid factory and one passing-case test.
  4. Add one invalid rule, watch it fail, then add only its validation.
  5. Repeat by rule family while keeping structured error assertions.
  6. Add mutation, sparse-ID, order, and unsupported-profile evidence.
  7. Review the public exports and browser production dependency graph.
  8. Run formatting, lint, both typechecks, build, and unit tests.
