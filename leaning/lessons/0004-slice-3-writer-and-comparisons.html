Lesson 4 · about 25 minutes

Write and compare without hiding changes

Slice 3 finishes the text boundary. Learn how to emit exact canonical COLMAP bytes, compare models by meaning, and separately prove that an unchanged model lost nothing.

Your tangible win: explain why one round trip needs two comparison results and sketch the writer/comparator blocks without receiving a finished implementation.

1. Slice 3 has three outputs

Canonical text

One deterministic representation of the validated model as three Uint8Array payloads.

Semantic result

Whether two models mean the same thing under approved floating tolerance and quaternion sign equivalence.

Exact result

Whether an unchanged model preserved every represented value, including the chosen quaternion sign.

A single “close enough” comparator cannot prove a no-op. It could accept a small drift or quaternion sign change and hide a writer bug.

2. Block A — validate before generating anything

The writer receives a TypeScript model, but runtime callers can still supply invalid values. Reuse the Slice 1 validator before building any output text. Do not validate file-by-file after some bytes already exist. 

validate complete model
→ build all canonical strings
→ encode all three strings
→ return all three payloads

This preserves the all-or-nothing boundary. The validator rejects rounding candidates, RGB values that would need clamping, non-unit quaternions, populated observations, and populated tracks. The writer does not repair any of them.

3. Block B — make one field string, then one record line

After validation, JavaScript's ordinary base-10 number string is the required numeric representation. Do not use toFixed or toPrecision: choosing a decimal width introduces rounding that the contract does not permit. 

String(1254.3877251148224) // round-trip-safe decimal
String(-0)                 // "0"

fieldStrings.join(" ")     // exactly one ASCII space

Build camera, image, and point lines from their fields in contract order. Keep the existing model-array order; never sort by ID. Sparse IDs are identifiers, not array indexes.

4. Block C — assemble exact physical lines

Treat each output file as an ordered array of physical lines. Start with the exact required header lines, append data records, join with LF, then append one final LF. 

lines.join("\n") + "\n"

For every image, append both the pose line and an empty string. That empty element becomes the required observation line. The last image still needs that structural empty line plus the file's final line ending. With zero points, points3D.txt contains only its three headers and final LF.

Preserve Canonicalize
Record order, IDs, names, references Headers and count text
Numeric values and quaternion representative Spaces, numeric lexemes, and line endings
Empty observation/track meaning Final LF and empty image lines

5. Block D — prove the writer ran

A round trip that returns the original text bytes could pass many model checks while never exercising the writer. Use one valid but noncanonical input: different comments, CRLF, extra accepted spacing, or an alternate valid numeric lexeme such as exponent notation. 

noncanonical bytes
→ parse model
→ serialize model
→ canonical bytes

original bytes !== canonical bytes

Then compare the canonical bytes against one complete golden string for each file. Partial contains assertions are too weak for headers, blank lines, field order, and final LF.

6. Block E — use the existing discriminated result

ModelComparison uses equal as a discriminant. When it is false, TypeScript exposes the stable path and reason. No exception is needed: unequal models are an expected verification result, not a malformed-input failure. 

if (comparison.equal) {
  // Only the success variant exists here.
} else {
  comparison.path;
  comparison.reason;
}

Keep these as pure exports from model-comparison.ts, not methods on the codec. The codec transforms text and models; the comparators answer questions about two models.

7. Block F — compare structure in one fixed order

Compare cameras first, then images, then points. Within each collection, compare record count, source order, and fields in a documented order. Return immediately on the first difference. 

{ equal: false,
  path: "images[2].pose.qvec[0]",
  reason: "quaternion-orientation" }

Stable zero-based paths make tests and later CLI diagnostics useful. They are model paths, not text line numbers. A text parser error says where input syntax failed; a comparison result says where two valid models diverged.

Choose the first failure

If the right model has one fewer image and a different point value, which difference must be returned? Explain why deterministic early return matters for repeatable tests.

8. Block G — exact fields stay exact

Both comparison strategies require exact counts, order, identifiers, camera model, dimensions, image names, camera references, RGB, and empty observation/track state. Floating tolerance must never leak into integer or identity fields.

Difference Example reason
Collection length record-count
Same records in another sequence record-order
Changed record ID identifier
Changed filename string-value
Changed width or RGB integer-value
Changed camera reference reference

To distinguish reordered records from changed IDs, first establish equal counts and compare the identifier sequence or membership. Do not sort before comparing: sorting would erase the source-order guarantee you are trying to test.

9. Block H — semantic floating comparison

Approved floating fields use a combined absolute and relative tolerance: 

Math.abs(a - b) <=
  Math.max(1e-12, 1e-12 * Math.max(Math.abs(a), Math.abs(b)))

The absolute floor handles values near zero. The relative part scales with larger magnitudes. Apply it only to intrinsics, pose components, point XYZ, and point error. Slice 1 validation already rejects NaN and infinity, so this helper does not need to invent behavior for them.

10. Block I — align quaternion signs semantically

A unit quaternion and its negation encode the same rotation. For semantic comparison, use their dot product to choose the right quaternion's sign, then compare aligned components with the floating predicate. 

dot(left, right) < 0
  ? compare left with -right
  : compare left with right

If the aligned components differ, report quaternion-orientation. Do not normalize either input—the validator must already have accepted both. Semantic comparison answers “same rotation?”, not “can these values be repaired?”

11. Block J — exact preservation is intentionally stricter

Exact no-op comparison uses exact JavaScript numeric equality for the represented values. Strict equality already treats -0 and 0 as equal, matching the writer's required zero canonicalization. Do not use Object.is, because it distinguishes their signs.

For quaternions, first ask whether the rotations are semantically equal. If they are equal only after sign reversal, exact preservation fails with quaternion-sign. If they encode different rotations, use quaternion-orientation.

Case Semantic Exact
0 versus -0 Equal Equal
Tiny approved float change within tolerance Equal Different
q versus -q Equal quaternion-sign
Different quaternion orientation quaternion-orientation quaternion-orientation

12. Keep the shared implementation boring

The two public functions traverse the same model structure. A small internal mode can select only the two rules that differ: approved float equality and quaternion sign handling. Do not build a generic deep-diff framework, configurable tolerance registry, or callback system. 

semantic wrapper ─┐
                  ├→ same deterministic field traversal
exact wrapper ────┘   with two numeric/quaternion policies

Straight loops and early returns are valuable here: they visibly encode source order and first-difference priority. Generic recursion would make field-specific reasons and quaternion behavior harder to review.

13. Minimum evidence for Slice 3

  1. Golden exact bytes for all three generated files.
  2. Zero-point output and an empty observation line per image.
  3. Repeated serialization produces identical byte arrays.
  4. Noncanonical valid input becomes canonical output.
  5. Parse → serialize → parse passes semantic comparison.
  6. The unchanged round trip separately passes exact preservation.
  7. q/-q passes semantic and fails exact.
  8. A tiny float change passes semantic and fails exact.
  9. Counts, order, IDs, references, integers, and strings fail exactly.
  10. The first failure returns its stable path and reason.
  11. Formatting, lint, both typechecks, build, and unit tests pass.
